These tools prepare Python programs and DWC plugins, on a Raspberry Pi or a Windows PC. There are two:

  • Prepare gets a Python project folder ready: it works out requirements.txt from the program's imports, creates the project's Python venv, installs requirements.txt into it with pip and checks that every package can be imported.
  • Copy Plugin Release Workflow copies the GitHub release workflow for DWC plugins into a plugin's folder on this computer. Once you commit and push those files, pushing a version tag to GitHub builds the plugin's ZIP and publishes a release.

Nothing is installed system-wide (no apt, no sudo): every package goes into the program's own venv, using the venv's pip. That works on Linux versions whose system Python is "externally managed" and refuses pip install.

What a project looks like

A project is any folder with a .py file in it or anywhere below it (venv, node_modules, __pycache__ and hidden folders are not looked in). Its name is the folder's name. One of its .py files is the main program (see Project options), and the folder the main program is in is the project's code folder: usually code, as below, but it can be any folder, such as Code/dsf in a DWC plugin. Nothing else needs adding: Prepare makes the rest.

scanCam/                   the project folder: its name is the project's name
    README.md              optional
    code/
        scanCam.py         the main program, which may set its version: progVersion = '1.0.0'
        requirements.txt   what pip installs into the venv: made by Prepare (it can also be in the project folder)
        ...
    venv/                  made by Prepare
    run.sh                 made by Prepare if there is none (Windows: run.bat): starts the program with the venv

Choosing the project

  • Type the full path of the project folder, or pick one of the recent projects the box offers. While you type, the box suggests the folders that fit (project folders have a project tag): pick one to carry on into it, or press Tab to complete the name. Or
  • press Browse… (on a narrow screen, the folder button next to the box). Click a folder to open it, or a part of the path at the top to go back up to it. Project folders are shown in bold with a project tag: press Select next to one, or Use this folder for the folder being shown. Type in the filter box to show only the folders whose names contain that text. Clicking a folder always opens it, project or not, as a project can hold other projects. From the keyboard: ↑ and ↓ move, Enter opens the folder, Ctrl+Enter selects it when it is a project, and Backspace goes up. The recent projects are at the bottom, one click away.

The project you choose comes back next time. Browse starts next to it.

Project options

Each project has options, under Project options below the project. They are saved as soon as you change them.

  • Main program: the .py file that starts the program, chosen from all the project's .py files. It is picked for you when it has the project's name (scanCam.py), is the only one, or is the only one at the top of a code folder. If it sets a version, with a line such as progVersion = '1.0.0' (__version__ or VERSION work too), Prepare shows it. A version is not needed.
  • The venv can also use Python packages already installed on the system (ticked by default): the venv then sees packages that came with the operating system, such as picamera2 on Raspberry Pi OS, as well as its own. Untick it for a venv that holds only what requirements.txt lists.

Prepare

  1. Choose the project and press Prepare. The line above the button shows what the project has now.
  2. requirements.txt. Every .py file in the code folder (and below it) is read for its import lines. Python's own modules and the project's own modules (any .py file or folder in the code folder) are skipped. Each other import is turned into the pip package that provides it, as recorded by the packages installed on this computer (for example yaml comes from PyYAML), or guessed from a short list of well-known names when it is not installed here (cv2 is opencv-python). The packages that are missing are added to the project's requirements.txt, which is made in the code folder if there is none. Nothing already in it is changed or removed, so your own additions and version pins stay. Packages it lists that nothing imports are reported. An import inside try: ... except ImportError: is optional, as the program copes without it: it is reported but not added.
  3. venv. The project's venv folder is created (with the system packages option above), or the existing one is used. A venv made with the other setting of that option is made again.
  4. Install. requirements.txt is installed into the venv with the venv's own pip.
  5. Check. The venv imports each package the program needs. A failure means something is missing from requirements.txt, or the package needs something from the operating system: the log shows the error.
  6. Launcher. run.sh (Windows: run.bat) is added to the project folder, unless there is one already, so the program can be run from there with its venv.

The log ends with the main program, its version, the requirements.txt used and the venv. Run Prepare again whenever the program's imports change.

Creating a venv needs Python's venv module. Debian and Raspberry Pi OS ship it separately as python3-venv: if the log says the venv could not be created, that package is missing and has to be installed once by the system administrator (sudo apt install python3-venv).

Copy Plugin Release Workflow

The workflow is kept in the plugin release workflow folder next to this app's program, laid out as it goes into a plugin's folder:

.github/workflows/release.yml      the workflow: builds the plugin's ZIP on GitHub and publishes the release
.github/workflows/release.yml.md   its notes: how to release, which DWC version is used, one-time setup
scripts/release.sh                 run it to tag and release the version in plugin.json
scripts/*.mjs                      helpers the workflow runs (release title, notes, files left out, ...)
scripts/release-channel.txt        settings: "latest" or "maintenance" for this branch
scripts/release-exclude.txt        settings: files to leave out of the ZIP
scripts/release-titles.txt         settings: the names used for release titles
  1. Choose the plugin's folder on this computer: the top of its git checkout (the folder holding .git), with the plugin's plugin.json in it or below it. Type its path, pick a recent one, or press Browse…, where folders with a plugin.json (in them or up to 3 levels below) have a plugin tag.
  2. The page lists every file of the workflow and what Copy will do with it: added (not there yet), replaced (there, but different), already the same, or kept. The three settings files are the plugin's own: one already in the repository is kept, so copying again to update the workflow never loses your settings. Tick Replace the plugin's settings files too to overwrite them with the ones from this app.
  3. Press Copy. Only the files in that folder change: Copy never commits or pushes. Commit the new files and push them yourself; that is when the workflow reaches GitHub.

Copy is refused when the folder is inside a git checkout but is not its top (GitHub only runs workflows from the top's .github folder), when there is no plugin.json, or when there is more than one and none at the top (the workflow would stop with an error). A folder that is not a git repository yet can be used: the workflow runs once it is on GitHub.

Once per repository on GitHub: allow Actions (Settings → Actions → General) and add an environment named exactly dwc-release-approval with yourself as a required reviewer (Settings → Environments). release.yml.md explains this and how to release.

What is remembered

The settings, the current project, the recent projects, each project's options and the plugin folders used with Copy Plugin Release Workflow are stored in one file, currently {{ c.settings_file || "..." }}. __HIDDEN_NOTE__ It is plain text, so you can back it up or delete it. Deleting it resets everything to the defaults. Venvs are made with {{ c.python || "..." }}, the Python outside any venv that this app's Python comes from.

Stop and Exit

  • Stop ends the running job in that tool, with everything it started (pip ...). Stopping Prepare part way can leave the venv without every package: press Prepare again.
  • Exit stops everything and shuts the app down (so does Ctrl+C in the terminal).
  • Closing the page does the same: once every page of the app has been closed, in every browser that had it open, the app stops any running job and shuts down about 10 seconds later. Going to another page of the app, or reloading, does not count, and nor does minimizing the browser, switching to another tab or app, or leaving the page alone for a long time: the app has no time limit. A page in front that stops answering (for example after the browser crashed) counts as closed after 90 seconds. If the browser crashes (or a phone closes the page in the background) while the app's page is hidden, the app keeps running: use Exit, or Ctrl+C in its terminal. Until a page has been opened for the first time, the app keeps waiting. So keep a page open while Prepare runs: closing it stops Prepare.
  • The Home page shows which tools are currently running.
